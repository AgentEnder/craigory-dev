BS CVEs and Maintainer Burnout

October 31, 2026

A Critical advisory lands against a package in your dependency tree. The gate goes red, a ticket opens somewhere downstream, and somebody has to work out whether it means anything.

Most of the time it does not. Finding that out is the expensive part, the fix ships anyway, and nothing about the software is safer than it was before.

About the examples

Some of what follows comes from Nx, the open source repository I work in every day. It is where I can show you a call site and where I have spent the afternoons, not a claim that Nx is unusual.

Nothing here says Nx is unsafe, or that the Nx team mishandles security. We read every report, work out whether it reaches us, and bump so nobody downstream carries something we could have taken off them. The complaint is about what the process costs to run, not whether to run it.

Scanners match version numbers instead of call graphs
#

Almost every advisory arrives with conditions attached. Something has to be handed a particular option, or reached from a request, before the bug is a bug at all.

npm audit, Socket and Dependabot do not check any of that. They check whether an installed version falls inside the affected range, because checking the conditions would mean resolving your call graph. For a library reached over the network, installed and reachable mostly coincide. There are two ways they come apart when the package is local developer tooling.

A 9.8 Critical your code cannot reach
#

Nx uses EJS to expand generator templates. The call site is three lines:⁠[1]Nx source, packages/devkit/src/generators/generate-files.ts. The only ejs.render call in the repository.

tspackages/devkit/src/generators/generate-files.ts
newContent = ejs.render(template, substitutions, {
  filename: filePath,
});

CVE-2023-29827 is rated 9.8 Critical: template injection through the closeDelimiter option, which lets you break out of the template and run arbitrary code.⁠[2]GitHub advisory GHSA-j5pp-6f4w-r5r6 (CVE-2023-29827), CVSS 9.8. Server-side template injection through the closeDelimiter option. Still listed as Unreviewed. A newer report does the same through escapeFunction.⁠[3]EJS issue #735. The same shape through opts.escapeFunction when opts.client is set, with the reporter's vector being an option merged in from a query string.

Both need an attacker to control the options object. Here it is a literal in the source with one key, and the key is the path of the file being rendered. The templates ship inside the generator package the developer installed, and substitutions are answers they typed into their own terminal. Editing any of that means already having write access to the developer’s disk, and anyone who has that has better options than EJS.

Despite being safe in our usage, we landed the bump to EJS 5.0.1 in 22.7.0.⁠[4]Nx pull request #35157, fix(core): update and pin ejs to 5.0.1, merged 2 April 2026 and first released in Nx 22.7.0.

A network attack you have to run on yourself
#

This one is different: the path is reachable and the bug fires exactly as written up. Nx works out which projects a command applies to by compiling patterns with minimatch:⁠[5]Nx source, packages/nx/src/utils/find-matching-projects.ts. Compiles each project pattern once and caches the resulting regex.

tspackages/nx/src/utils/find-matching-projects.ts
const regex = minimatch.makeRe(pattern, { dot: true });

Compiling a pattern runs brace expansion, which is where CVE-2022-3517 lives. A crafted pattern sends braceExpand into catastrophic backtracking and pins a core, scored 7.5 High for an attacker who reaches it over the network with no privileges and no user interaction.⁠[6]GitHub advisory GHSA-f8q6-p94x-37v3 (CVE-2022-3517), High, CVSS 7.5, vector AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H. ReDoS in braceExpand for minimatch below 3.0.5.

The pattern comes from nx.json or a --projects flag somebody typed. Exploiting it means putting a pathological glob in your own config on your own laptop and waiting while your own build hangs. You are the only victim, and you find out in the ten seconds before you kill the process and fix the glob.

Every build tool that has ever expanded src/**/*.ts gets handed the same 7.5. minimatch delegates brace expansion to brace-expansion, which Nx pins by override, and that pin moved twice in a week when the version it took on 29 July was called incomplete the next day.⁠[7]Nx pull requests #36507 (merged 29 July 2026, brace-expansion 5.0.6 to 5.0.8) and #36577 (merged 5 August 2026, 5.0.8 to 5.0.9), both of them pins in the overrides block of pnpm-workspace.yaml rather than a declared dependency. GitHub advisory GHSA-rgw5-rvv9-x895 (CVE-2026-69152, High, CVSS 7.5), published 30 July 2026, records that the maxLength mitigation added in 5.0.8 for CVE-2026-14257 was incomplete. Both pins sit in 23.2.0 prereleases; the newest stable release is 23.1.2.

Nobody upstream decides whether it applies to you
#

Both of those numbers are defensible somewhere. CVSS scores the worst context anyone can construct, which is the right question to ask about a library that renders web responses for strangers.

The database stores one score, and every consumer downstream reads that one. A CLI running on your laptop against files you wrote has a different threat model than an Express handler, and there is no field for that.

The largest issuer in the ecosystem is candid about this. The Linux kernel became its own numbering authority and now assigns CVEs out of the stable release process, on the stated grounds that “almost any bug might be exploitable to compromise the security of the kernel, but the possibility of exploitation is often not evident when the bug is fixed”, so the team is “overly cautious and assign CVE numbers to any bugfix that they identify.”⁠[8]Linux kernel documentation, CVEs. The kernel is its own CVE Numbering Authority and assigns numbers from the stable release process.

The same document is explicit about who is left holding the question:

That is an honest description of the division of labour, and it is the work this whole post is about, assigned downstream in a sentence.

Every alert costs a maintainer an afternoon
#

Both of those took reading a call site to settle. A scanner that does read the code hands over a different problem, and not a smaller one.

Flagged for doing its job
#

esbuild is a bundler. It reads your files, spawns a native binary and writes new files, and Socket’s alert page is a fair summary of what a scanner makes of that:

Accurate, and load-bearing. Install scripts, Network access and Dynamic require sit beside it, each describing something a bundler does on purpose. You install esbuild precisely so that it will run a binary against your filesystem, and there is no version to bump to. The finding recurs on every scan for as long as the package does what it says on the tin.

Four findings and an afternoon
#

Socket’s page for nx carries that same set, and one more above it:

Behind that summary, each instance carries a confidence score, an impact score, the file it fired on, and a paragraph of reasoning. One flags v8.deserialize on socket payloads. Another flags execSync on a command string assembled from CLI arguments. That is a good deal more than the summary line suggests, and the summary line is what reaches a dashboard.

Working out whether any of it reaches you means finding each call site and reasoning about who can supply the input.

For those four that was an afternoon, and most of the threat models did not survive contact with the code: the socket is a unix socket the daemon chmods to 0600, and the commands come from config files in your own repository. That afternoon is not free, and nothing in the pipeline that raised the alert helps you spend it.

Compiled code gets a pass
#

Everything above is a false positive: an alert firing on code that cannot hurt you. Scanners are also quiet in places, and the quiet is not a verdict either.

esbuild ships in two halves. The JavaScript half is the esbuild package, and it drew the alerts above. The other half is a compiled Go binary, published as one package per platform and pulled in as an optional dependency so the installer takes the one matching your machine.

@esbuild/darwin-arm64 is three files: a 145-byte README, a 382-byte package.json, and 10.1 MB of compiled binary.⁠[11]@esbuild/darwin-arm64 0.28.2 contains bin/esbuild at 10,590,882 bytes, a 382-byte package.json and a 145-byte README.md. Socket’s page for it, same version and same release as the alerts above, reads in full:

Nothing there is a finding about the binary, and I am not suggesting one is hiding in it. It is a statement about what a scanner can read. Static analysis needs source, and the advisory databases are indexed by package name and version, which is not a thing anyone files against a blob.

That split is now normal. SWC and Rollup publish prebuilt Rust binaries the same way, and Nx ships its own Rust core in ten platform packages beside the JavaScript one.⁠[13]npm registry metadata, read 31 August 2026: @swc/core-darwin-arm64 ships 4 files and 24.8 MB, and @rollup/rollup-darwin-arm64 3 files and 1.8 MB. Nx lists ten platform packages such as @nx/nx-darwin-arm64 (three files, 18.4 MB) as optional dependencies of nx. Whatever a dashboard reports for those packages was decided by the language their authors chose, not by what the code does. The JavaScript half of a tool gets read closely and answers for every line. The half that got rewritten for speed is not being cleared, it is being skipped.

Three ways to say no that all fail
#

Having spent the afternoon, a maintainer has three moves, and all three are worth roughly nothing.

Write the boundary down
#

The EJS maintainers wrote their position down. Their security policy says that giving end users unfettered access to the render method is “using EJS in an inherently un-secure way”, and that “EJS is effectively a JavaScript runtime. Its entire job is to execute JavaScript.”⁠[14]EJS SECURITY.md, which scopes out reports arising from passing unsanitized user input to the render method. That is a boundary drawn in public, in the file the process tells you to read, and reports keep arriving anyway.

Lodash went further and published a threat model: a document naming what the library trusts and what it does not. The code calling Lodash is trusted, so passing attacker-controlled data straight into a Lodash function “is an application bug, not a Lodash vulnerability.”⁠[15]Lodash threat-model.md, linked from its SECURITY.md. It names what Lodash trusts, including "the code that invokes Lodash", and lists out-of-scope report classes such as unvalidated application input and prototype pollution via trusted code.

Its commit history is a record of the reports it did not stop. The threat model landed in October 2025. A security notice for _.template was added to it in February 2026. Two more advisories were published against Lodash on 1 April 2026, and three weeks after that a commit added exclusions for common report patterns, among them a section explaining that getters and proxies are code rather than data.⁠[16]Commits to threat-model.md: #6026 added it (27 October 2025), #6099 added a _.template security notice (6 February 2026), and #6203 added "threat model exclusions for common report patterns" (22 April 2026). GitHub advisories GHSA-r5fr-rjxr-66jc and GHSA-f23m-r3pf-42rh were both published on 1 April 2026, between the second and third. Somebody had been filing that one often enough to be worth a heading.

Dispute the score
#

Disputing is allowed and accomplishes very little. NVD records the dispute for CVE-2023-29827 in the description itself:

That same record carries a Primary CVSS of 9.8 Critical, assigned by NVD. The dispute is prose. The score is a field. GitHub marks the advisory Unreviewed so Dependabot skips it, and every scanner pulling from NVD directly still reports the 9.8.⁠[18]GitHub Docs, About the GitHub Advisory Database. Unreviewed advisories are published automatically from the NVD feed and do not raise Dependabot alerts.

Publish a machine-readable “not affected”
#

VEX and CSAF let a publisher declare a product unaffected by an advisory, which is exactly the statement a maintainer wants to make.⁠[19]OASIS, CSAF 2.0, which defines the VEX profile a publisher uses to state that a product is not affected by an advisory. Consuming-side adoption is thin enough that publishing one gets you out of nothing today.

You bump anyway
#

A published advisory naming your package is permanent, and most people who meet it will never read your explanation. “Critical RCE in your-package” travels further than any threat model you write down.

Nobody is penalized for over-reporting, and a maintainer who declines to bump inherits every downstream user’s compliance ticket. CVE-2023-42282 is the shape of it: an SSRF in the ip package, rated Low by GitHub, where isPublic() misreads private addresses written in unusual formats. That matters if you gate a sensitive path on the result, and does not if you never call it. Searching GitHub for the CVE returns more than four hundred issues carrying it in the title, many opened by a scanner rather than a person and most of them labelled Critical, on projects including Node’s official Docker images, semantic-release, pm2 and the Actions runner.⁠[20]GitHub advisory GHSA-78xj-cgh5-2h22 (CVE-2023-42282), severity Low. A GitHub issue search for the CVE ID returned 408 results on 31 August 2026, the visible majority titled "CVE-2023-42282 (Critical) detected in ip-1.1.5.tgz" by the scanner that filed them. Examples: nodejs/docker-node#2039, semantic-release#3202, pm2#5761 and actions/runner#3245.

Those maintainers are not being written to because somebody read the advisory and disagreed. They are being written to because a scanner failed somebody’s pipeline and their name was attached to it.

You bump, and most of the time it is cheap: the fixed version already sits inside the declared range, so it costs a lockfile line and a patch release. Sometimes there is nothing to bump to, as with GHSA-j5pp-6f4w-r5r6, which lists no patched version at all. Either way the release buys no security. It buys a green scanner.

Some caveats
#

Bump anyway, most of the time. The release is cheap, and being right about reachability does not travel. The argument lives in a thread somebody has to go and find, while the advisory shows up in every scan a prospective user runs before they adopt you. A package that reads Critical on a dashboard loses people who were never going to open the thread.

Who pays
#

The user learns to ignore it
#

Dan Abramov went through five advisories against a fresh Create React App in 2021. None were exploitable there, and he named the real damage:

The training worked, and the tooling shipped the evidence:

  • --audit-level, so a team can pick a severity beneath which the output stops failing the build.
  • --omit=dev, so build-time packages stop counting at all.

Those flags exist because the output was unusable without them.⁠[22]npm CLI documentation, npm audit. --audit-level sets the minimum severity that exits non-zero; --omit=dev drops devDependencies from the report. Past that come the local habits: the audit step piped to true, the allowlist entry that outlives everyone who understood why it was added. Every one of those is a rational response to a channel that has never carried anything worth reading.

The code gets deleted
#

The kernel is where the volume is easiest to see. CVEs fixed per release ran around 500 through the 6.x series. Every release since 7.0 has been over a thousand, 7.2 passed 1,500, and 7.3 is on course for 2,000.⁠[23]Michael Larabel, The Linux Kernel Is Approaching 2,000 CVEs Per Release, Phoronix, 28 August 2026, reporting a slide from Greg Kroah-Hartman ahead of Kernel Recipes 2026. Linux 6.9 through 6.19 averaged roughly 500 CVEs fixed per release; every release since 7.0 has been over a thousand, and 7.2 passed 1,500. That is not a change in how secure the kernel is. It is AI tooling reading forty million lines of code that nobody previously had a reason to read.

Reviewing the networking pull request for 7.3, Jakub Kicinski put between a third and a half of its 648 patches down to low-priority work from that tooling:

Part of the response has been to delete things. A proposal went up in April to remove nearly 28,000 lines of networking drivers for ISA and PCMCIA-era hardware, and the FreeVxFS filesystem driver was removed after its maintainer noted that the decades-old compatibility code now mostly served as fodder for automated bug checkers. Those drivers were cheap to keep for as long as nobody was looking at them. They stopped being cheap when tools started finding defects in them that somebody was then obliged to answer for.

Nobody decided that the hardware had stopped mattering. Scanning got cheap, answering did not, and the code that could not pay for its own triage went.

The maintainer goes quiet
#

The other half of the bill goes to whoever answers. Through 2025 about a fifth of curl’s security submissions were AI slop, at roughly two a week, and the share that turned out to be real fell from north of 15% to under 5%.⁠[25]Daniel Stenberg, Death by a thousand slops, July 2025. Roughly 20% of 2025 submissions were AI slop, at about two security reports a week.

Each one has to be read by somebody who can tell, and Stenberg puts the cost at three or four people per report, thirty minutes to three hours each, on a submission that describes nothing.

In January 2026 curl ended its bug bounty. Seven years, 87 confirmed vulnerabilities, more than 100,000 USD paid out, shut down because the reports stopped being worth reading.⁠[26]Daniel Stenberg, The end of the curl bug-bounty, January 2026. Seven years, 87 confirmed vulnerabilities, over 100,000 USD paid, closed to GitHub private disclosure and email on 31 January 2026. The program did not end because curl ran out of bugs. It ended because finding them stopped being possible at a price anyone would pay.

Seth Larson, who triages security reports for CPython, pip, urllib3 and Requests, named where that ends:

Attention is the scarce resource in maintenance, and every part of this spends it on reports that turn out to be nothing. People go quiet, or hand the keys to whoever volunteers. The handover is the dangerous one. In June 2022 the maintainer of xz was being told in public that he had “lost interest or doesn’t care to maintain anymore”, and answered:

The account applying that pressure is widely assessed to have belonged to the operation that put a backdoor in xz two years later, as CVE-2024-3094.⁠[29]CVE-2024-3094. Malicious code introduced into the xz upstream releases by an account that had spent roughly two years gaining commit access. That campaign was about release velocity rather than advisory noise, so I am not claiming npm audit produced it. The resource it drained is the same one. A maintainer’s attention is a security property of the package, and the current process treats it as free.

What would actually help
#

Socket and Snyk both sell reachability analysis, which asks a better question than npm audit does. It is not what most CI gates run, and it still only reads the code that ships as source.

The scanner asks whether a version is installed. The maintainer has to answer whether anyone can actually do the thing. Until the second question is as cheap as the first, the difference gets paid in releases that change nothing and in the people who stop answering. The advisories that do apply arrive through the same channel, at whoever is left.
